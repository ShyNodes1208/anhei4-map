# Project Development Rules

Applies to: Claude, Cursor, Codex. All stages and tasks.

---

# 最小实现与禁止过度开发原则

## 1. 只实现当前明确需求

所有 Agent 只能实现：用户明确提出的需求、当前任务单明确列出的内容、完成当前目标不可缺少的最小技术支撑。

不得因为"以后可能有用"而提前增加功能、接口、配置、抽象层或基础设施。

## 2. 禁止未经批准的附加功能

未经用户明确批准，不得主动增加：配置界面、插件系统、通用框架、多套实现策略、历史版本管理、自动清理系统、复杂缓存、数据库、服务端、云端能力、遥测、用户行为统计、自动更新、多语言、多主题、复杂日志平台、不属于当前需求的异常恢复体系、不属于当前问题的兼容层。

## 3. 优先采用最小可行修改

处理问题时优先顺序：1) 修正现有代码中的明确错误；2) 复用现有结构和接口；3) 增加最少量代码完成目标；4) 只有现有结构确实无法满足时，才允许新增类或模块；5) 任何新增抽象必须能说明当前需求为什么离不开它。

## 4. 禁止为单一问题建设通用平台

不得为了一个局部问题建设：通用诊断平台、通用工作流引擎、通用任务框架、通用存储层、通用插件架构、复杂状态机、多层服务封装。当前问题只需要一次性脚本、一个方法或一个小类时，不得扩展成大型子系统。

## 5. 新增文件和类必须经过必要性检查

每增加一个文件、类、接口或依赖，任务单必须回答：当前需求为什么需要它？不增加它是否仍能完成需求？是否可以直接复用现有代码？是否可以用更少的文件完成？是否会引入长期维护成本？无法给出明确理由时，不得增加。

## 6. 禁止提前实现后续阶段功能

当前任务不得提前实现：后续任务内容、尚未批准的候选方案、用户尚未要求的增强功能、"顺手实现"的优化、与当前验收无关的重构。发现后续需求时，只记录到文档，不得写入生产代码。

## 7. 诊断代码必须最小化

诊断功能只收集解决当前问题必需的证据。不得默认增加：多 run 历史管理、容量管理平台、自动清理系统、复杂 manifest 状态机、大型错误矩阵、iframe 全量扫描、shadow DOM 全量遍历、完整 DOM 导出、通用截图标注框架、多层诊断服务。除非当前问题有直接证据证明这些能力不可缺少。

## 8. 依赖和技术选型限制

不得为了方便而随意增加 NuGet、第三方库或外部服务。新增依赖前必须证明：.NET/WPF/WebView2 现有能力无法合理完成；新依赖直接解决当前明确需求；引入收益高于安装、升级、安全和维护成本；已获得用户批准。

## 9. 任务派发必须写明"不做什么"

每个任务必须包含：本任务目标、最小允许修改路径、明确禁止内容、本任务不实现的后续功能、验收标准。不得使用"根据需要增加其他文件"或"可顺便优化"等开放式授权。

## 10. Agent 职责

Claude：应主动压缩方案复杂度；不得把简单需求拆成不必要的大型架构；派发前必须检查是否存在过度设计；发现方案超过当前需求时必须缩减。

Cursor：只能实现任务单内容；不得自行重构无关代码；不得提前实现后续功能；不得新增未批准文件、类、依赖和配置。

Codex：审核时必须检查是否引入多余功能、是否存在过度抽象、是否增加无必要文件或依赖、是否超出用户当前需求、是否可以用更小改动完成。发现过度开发时应作为正式 Finding 报告。

## 11. 决策原则

当"完整但复杂"和"足够且简单"都能满足当前需求时，必须选择足够且简单。只有具备以下证据时才允许选择复杂方案：简单方案已经验证不可行、当前需求明确要求复杂能力、存在具体而非假设性的风险、用户明确批准。

## 12. 验收门禁

任何任务提交前必须确认：没有增加用户未要求的功能、没有提前实现后续阶段、没有不必要的新依赖、没有不必要的新文件或抽象、修改范围是完成任务所需的最小范围、删除这些新增内容后，当前需求是否仍能完成。如果最后一项答案是"能"，则该新增内容应删除。
